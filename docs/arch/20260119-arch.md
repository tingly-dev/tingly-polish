
**Design Patterns:**
- **Container/Presentational**: Separate logic from UI
- **Custom Hooks**: `useConfig`, `useHistory`, `useLLM`
- **Context**: `ExtensionContext` for global state

### 2. Content Script Layer (`src/content/`)

```
content-script.ts (Entry)
├── InputMonitor
│   ├── detectTripleSpace()
│   └── dispatchTrigger()
├── TextReplacer
│   ├── replaceInputElement()
│   └── replaceContentEditable()

    ├── handleTranslate()
    └── handlePolish()
```

**Responsibilities:**
- Inject into all web pages
- Monitor all input elements for triple space
- Coordinate with background service
- Perform text replacement in DOM

## Key Design Patterns

### 1. Repository Pattern
Abstract storage operations behind interfaces:

```typescript
interface IConfigRepository {
  getConfig(): Promise<Config>;
  updateConfig(config: Partial<Config>): Promise<void>;
  resetToDefault(): Promise<void>;
}

interface IHistoryRepository {
  addEntry(entry: HistoryEntry): Promise<void>;
  getHistory(): Promise<HistoryEntry[]>;
  clearHistory(): Promise<void>;
}
```

### 2. Adapter Pattern
LLM clients implement common interface:

```typescript
interface ILLMClient {
  translate(text: string, config: Config): Promise<string>;
  polish(text: string, config: Config): Promise<string>;
  isAvailable(): boolean;
}
```

### 3. Message Bus Pattern
Decoupled communication:

```typescript
interface IMessageBus {
  subscribe<T>(channel: string, handler: (data: T) => void): () => void;
  publish<T>(channel: string, data: T): Promise<void>;
  request<T, R>(channel: string, data: T): Promise<R>;
}
```

### 4. Factory Pattern
Create appropriate LLM client based on config:

```typescript
class LLMClientFactory {
  static create(config: Config): ILLMClient {
    if (config.useMock) return new MockLLMClient();
    return new OpenAIAdapter(config);
  }
}
```

### 5. Observer Pattern
React on configuration changes:

```typescript
class ConfigPublisher {
  private subscribers: Set<ConfigChangeListener>;

  subscribe(listener: ConfigChangeListener): () => void;
  publish(config: Config): void;
}
```

## Data Flow

### Translation Flow

```
1. User types "   " (triple space) in input
   ↓
2. InputMonitor detects pattern
   ↓
3. Content Script sends message to Background
   ↓
4. Background gets text, saves to history
   ↓
5. LLM Client calls API (or mock)
   ↓
6. Response returned to Content Script
   ↓
7. TextReplacer updates DOM element
   ↓
8. User sees translated text
```

### Config Update Flow

```
1. User changes API key in Popup
   ↓
2. ConfigPage updates local state
   ↓
3. useConfig hook calls ConfigRepository
   ↓
4. Chrome Storage updated
   ↓
5. ConfigPublisher notifies subscribers
   ↓
6. Background Service recreates LLM Client
   ↓
7. New config active for next request
```

## State Management

### Storage Schema

```typescript
// Chrome Storage Areas
chrome.storage.local {
  // Extension configuration
  'config': {
    apiKey: string;
    baseUrl: string;
    model: string;
    systemPrompt: string;
    userPrompt: string;
    useMock: boolean;
  },

  // Input history
  'history': HistoryEntry[],

  // Runtime cache
  'cache': {
    [key: string]: { response: string; timestamp: number; }
  }
}

chrome.storage.sync {
  // Optional: sync key settings across devices
  'syncConfig': {
    apiKey?: string;  // Encrypted
  }
}
```

## Security Considerations

1. **API Key Storage**: Use `chrome.storage.local` (not sync for keys)
2. **Content Security**: Sanitize all text before DOM injection
3. **CORS Handling**: Background service makes API calls
4. **Input Validation**: Validate all config values

## Performance Optimizations

1. **Debounce**: Input detection debounced by 300ms
2. **Cache**: LLM responses cached for 1 hour
3. **Lazy Load**: Popup components code-split
4. **Web Worker**: Heavy processing in background
5. **Rate Limiting**: Prevent API spam
